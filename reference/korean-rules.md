# 한국어 작성 규칙

lint는 A절의 일부 표현과 길이만 검토 후보로 찾는다. 문법 오류나 번역체를 확정하지
않는다. B·C절과 수정 여부는 독자·장르·문맥을 읽고 판단한다.

## A. 문장 — 기계로 검사되는 것

1. **길이와 호흡을 확인한다.** 80자를 넘으면 구조를 살피고, 100자를 넘으면
   분할을 우선 검토한다. 괄호 속 근거·예시와 "범위: a, b, c" 같은 열거는 길이에 넣지
   않는다. 조건·예외가 필요한 문장을 짧다는 이유로 잘라 뜻을 잃지 않는다.
2. **관형절이 겹치면 지시 대상을 확인한다.** 독자가 수식 대상을 놓칠 때만 푼다.
3. **`~에 대한` / `~에 대해`는 목적어 관계가 분명할 때 줄인다.**
   `X에 대한 검증` → `X를 검증`. `권한에 대한 설명`처럼 뜻이 달라지면 유지한다.
4. **`~을 통해` 재고.** 도구면 `~로`, 경로면 `~를 거쳐`, 원인이면 `~라서`.
5. **`~에 있어서`는 더 직접적인 관계가 있을 때 바꾼다.** `~에서`, `~할 때` 등.
6. **명사 + 빈동사 합치기.** `검증을 수행한다` → `검증한다`.
   대상 동사: 수행·진행·실시·시행하다.
7. **`의`가 겹치면 관계를 분명히 한다.** 풀어 쓰면 오히려 길어질 때는 유지한다.
8. **피동의 행위자와 초점을 확인한다.** `되어지다` 같은 중복형은 고치되,
   행위자가 알려지지 않았거나 결과가 중심인 피동은 유지한다.
9. **주어가 자연스러운지 본다.** `이 PR은 ~한다`, `함수가 값을 반환한다`처럼 기술
   문서에서 굳은 무생물 주어는 쓸 수 있다. 무생물이 사람 행동을 하면 고친다 —
   `이 필드가 횟수를 말해 준다` → `이 필드에 횟수가 담긴다`,
   `캐시가 오래된 값을 뺀다` → `오래된 값은 캐시에서 빠진다`.
10. **빈 동사를 살핀다.** <!-- lint-skip -->`존재한다`·`제공한다`가 실제 의미를 담으면 유지한다.
11. **확신의 정도를 보존한다.** `~인 것으로 보인다`가 관찰에서 나온 추정이면
    단정하거나 단순한 미확인으로 바꾸지 않는다. 불필요한 완곡 표현일 때만 덜어낸다.
12. **`해당 X` 재고.** `그 X` 또는 이름을 직접 쓴다.
12-1. **(prose 프로필) 영어 구를 조사로 잇지 않는다.** `source of truth이고`, `dispatch validation failure는`
    처럼 번역하지 않은 영어 구에 조사를 붙이면 한국어 문장 한가운데에서 읽기가 끊긴다.
    일반 영어 구는 한국어로 쓰고, 코드면 백틱, 팀이 영어로 굳힌 용어(`refresh token`
    등)는 그대로 둔다. 한 단어(`cache를`)는 대상이 아니다. 기본인 coding 프로필에서는
    영어 구를 그대로 두고 둘레의 한국어만 고친다.
12-2. **대시 둘로 삽입구를 끼우지 않는다.** `쓰기 — 계정 조치 포함 — 는`처럼 영어식
    삽입구를 문장 가운데 넣으면, 서술어가 끝에 오는 한국어 어순이 끊긴다. 괄호로 옮기거나
    문장 뒤로 뺀다.

## B. 문단 — 정보 구조

13. **독자가 먼저 필요한 정보를 앞에 둔다.** PR·안내문은 결론이 앞에 오기 쉽다.
    서사·연구 설명은 근거를 쌓은 뒤 결론을 제시할 수도 있다.
14. **은/는과 이/가의 초점을 살핀다.** 처음 등장했다고 반드시 `이/가`를 쓰는
    것은 아니다. 대조·화제·강조에 따라 달라진다.
15. **한 문단 한 주제.** 주제가 바뀌면 문단을 나눈다. 5문장을 넘으면 대개 두 주제다.
16. **연결어는 관계가 있을 때만.** `또한`, `그리고`를 접착제로 쓰지 않는다.
    앞뒤가 대조면 `반면`, 인과면 `그래서`, 아니면 그냥 새 문장으로 둔다.
17. **독자가 비교하거나 실행해야 할 때 목록을 쓴다.** 개수만으로 산문을 목록으로
    바꾸지 않는다.

## C. 문서 — 읽는 사람 기준

18. **독자가 무엇을 알아야 하거나 해야 하는지 드러낸다.** 순서는 장르에 맞춘다.
19. **왜를 쓴다.** 무엇을 바꿨는지는 diff가 말해준다. 왜 그렇게 했는지, 무엇을
    포기했는지는 글만 말할 수 있다.
20. **모르면 모른다고 쓴다.** 확인 안 한 것을 확인한 것처럼 쓰는 게 가장 비싼 실수다.
21. **용어를 고정한다.** `reference/glossary.md` 참조. 한 문서 안에서 같은 것을
    두 이름으로 부르지 않는다.
22. **읽는 흐름을 확인한다.** 소리 내어 읽거나 문장을 다시 훑되, 길이 하나만으로
    수정 여부를 결정하지 않는다.

## 하지 말아야 할 과교정

규칙을 기계적으로 밀면 다른 종류로 나빠진다.

- **기술 용어를 억지로 번역하지 않는다.** `commit`, `cache`, `rollback`은 그대로 둔다.
  한국어 단어가 이미 정착한 것만 한국어로 쓴다(`저장소`가 아니라 `repository`처럼,
  팀이 실제로 쓰는 쪽을 따른다).
- **코드 심볼은 절대 번역하지 않는다.** 함수·클래스·필드 이름은 원문 그대로 백틱 안에.
- **짧게 만든다고 정보를 버리지 않는다.** 문장을 쪼개는 것이지 내용을 줄이는 게 아니다.
- **구어체로 흐르지 않는다.** 자연스러움이 목표지 친근함이 목표가 아니다.
  기술 문서의 기본은 평어체 서술문이다.
- **`~에 대한`을 없애려고 문장을 비틀지 않는다.** 조사로 안 풀리면 문장 자체를
  다시 설계하거나 그대로 둔다.
- **추정·조건·의무를 더 강하게 바꾸지 않는다.** 문체보다 명제의 범위가 우선이다.
